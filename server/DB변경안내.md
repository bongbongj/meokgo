# 조건 기반 후보 선정 DB 변경 안내

> 작성자: 정효림
>
> 작성일: 2026-10-31
>
> 참조: `reference/API명세서.md`, `reference/DB설계서.md`

## 1. 적용 범위

신규 DB와 로컬 H2는 엔티티 기준으로 테이블을 생성한다. 이번 검증은 H2에서 수행하며, 기존 MySQL 데이터의 변경 작업은 자동 실행하지 않는다.

현재 `ddl-auto: update` 설정은 기존 데이터의 의미 변환이나 사용하지 않는 컬럼 삭제를 대신하지 않는다. 기존 데이터가 있으면 서버 적용 전에 아래 순서로 별도 이관한다.

## 2. 탐험 조건 데이터

`exploration_condition`에 `recognized_avoid_keywords` JSON 컬럼과 `dictionary_version`을 먼저 NULL 허용으로 추가한다.

- 기존 `avoid_foods` 원문은 보존한다.
- 원문이 비어 있으면 기피 키워드 배열을 빈 배열로, 사전 버전을 `1`로 채운다.
- 원문이 있으면 새 해석 서비스와 동일한 사전으로 재해석한다. 모호한 표현을 임의로 빈 배열로 바꾸지 않고 확인·수정한 후 결과를 채운다.
- 모든 행의 해석 결과가 채워졌는지 확인한 뒤 두 컬럼에 NOT NULL 제약을 적용한다.
- 기존 `budget_min`, `budget_max`는 새 코드에서 사용하지 않는다. 물리 컬럼 삭제는 기존 데이터 보관 정책 확인 후 별도 수행한다.

이전 개발 버전에서 허용 키워드 컬럼을 생성한 환경에서는 새 코드가 해당 컬럼을 사용하지 않는다. 해당 컬럼에 NOT NULL 제약이 있다면 신규 방 저장을 막지 않도록 먼저 NULL을 허용한다. 물리 컬럼 삭제는 데이터 보관 정책 확인 후 별도 수행한다.

## 3. 퀘스트와 후보 데이터

`quest`에 음식·충돌 키워드와 활동·호불호·경쟁 여부 컬럼을 추가하고 기존 데이터를 검수하여 채운다. 새 Boolean 컬럼은 기존 행에 0을 채운 후 NOT NULL을 적용한다. 키워드는 사전의 표준 키워드를 쉼표로 구분하여 저장한다.

기존 `LOCAL` 퀘스트는 지역과 무관하게 수행 가능한지 검수한다. 사용 가능한 항목을 적절한 공통 행동 유형으로 변환하고, 사용할 수 없는 항목의 기존 기록 보존 방식을 정리한다. 새 코드 적용 전에 `LOCAL` 값이 남지 않도록 처리한다.

`room_quest_candidate.completed_participant_count`를 추가한다. 기존 후보는 당시 참여자·이력 기준을 복원할 수 있는지 확인하여 채우고 `suppressed_by_history_yn`과 일치시킨다. 과거 집계를 복원할 수 없는 후보를 새 규칙으로 생성된 결과라고 표시하지 않는다.

`room_id, quest_id` 및 `room_id, candidate_order`의 기존 중복 여부를 확인하고, 이력을 보존하여 정리한 후 유일 제약을 적용한다. 기존 후보 목록을 임의로 재추첨하지 않는다.

## 4. 완료 이력

`user_quest_history` 테이블과 `user_id, quest_id` 복합 인덱스를 추가한다. 동일 사용자의 반복 완료 이력은 보존하고 후보 선정 시 서로 다른 사용자 수로 집계한다. 과거 완료 데이터가 없다면 이력을 임의로 생성하지 않는다.

## 5. 적용 확인

- 자유 입력 원문과 표준 기피 키워드가 함께 보존되는지 확인한다.
- 비음주 조건과 음식 충돌 필터가 적용되는지 확인한다.
- 전체 참여자의 완료 경험자 수가 적은 순으로 후보가 선정되는지 확인한다.
- 기존 후보 재조회에서 후보 ID와 노출 순서가 유지되는지 확인한다.
- 기존 클라이언트가 예산 필드를 사용하지 않고 `filled_with_history_quest`를 읽도록 함께 반영한다.

## 6. 투표 마감과 최종 퀘스트 확정

- `vote`에 마감 시 미투표 인원·확인값·마감 일시와 `tie_break_candidate_ids`, `tie_break_host_participant_id`를 추가한다. 기존 열린 투표의 확인값은 0, 마감 정보와 동점 선택은 NULL로 유지한다. 기존 마감 데이터는 실제 상태를 검토하여 이관한다.
- `tie_break_host_participant_id`는 `room_participant`를 참조한다. 후보 JSON 배열의 소속과 개수는 서비스가 검증한다.
- `vote_item`의 `vote_id, participant_id, candidate_id` 중복을 확인·정리한 후 유일 제약을 적용한다.
- `final_quest` 테이블과 방·후보, 방·순위 유일 제약 및 관련 외래키를 추가한다. 기존 확정 데이터가 있으면 ID·선정 순위·사유를 보존한다.
- 신규 H2 DB 생성과 API 테스트는 자동 검증하며, 기존 MySQL 데이터 이관은 별도 적용한다.

## 7. 참여 복구·탐험 진행·기록 조회 보완

참조 기준은 `reference/API명세서.md`의 6·7·11·12장 및 `reference/DB설계서.md`의 6.7·6.13·6.14절이다.

- `room_participant`의 `room_id, user_id` 및 `room_id, nickname` 유일 제약을 엔티티에도 적용했다. 기존 MySQL에 중복이 있으면 참조된 투표·진행·기록을 보존하는 이관안을 확인한 뒤 제약을 적용한다. 기존 데이터는 자동 삭제하지 않는다.
- 신규 `quest_progress`, `exploration_record` 테이블과 외래키·인덱스를 확인한다. 기존 `user_quest_history`에는 종료 시점의 실제 완료 항목만 추가한다.
- 기존 `last_connected_at`은 실제 접속을 보장하지 않는다. 적용 후 정상 방 요청에서 갱신하며 기본 유효 시간은 30초다.
- 미종료 방의 `expired_at`이 지나면 기본 60초 주기로 `EXPIRED`로 전환한다. `FINISHED` 상태와 저장된 기록은 유지한다.
- H2 통합 테스트로 동시 입장·권한 이전과 복구·기록 조회를 검증했다. MySQL의 기존 데이터 이관 및 잠금 동작은 이 환경에서 실행하지 않았다.
